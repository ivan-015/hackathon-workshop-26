Blocking findings AI reviews always find nits/small issues with your PRs. For a hackathon, it's important to focus on the high priority, blocking findings.

Make it visible: ask for the findings as a one-page HTML report, or a Claude artifact.

RUN: window 1 first, start the loop: /loop check whether CI passed and address any review comments. Then window 2 (cd into the repo first): /pstack:interrogate the open PR, then post the “act on” findings as review comments with gh. Open the PR tab and watch the comments land, then window 1 picks them up, pushes a fix and replies. When the PR is green and quiet, press Esc in window 1 to stop the loop. FALLBACK: show the rehearsal PR’s conversation, which already has the comments, fixes and replies. —— This is the writer/reviewer pattern: the reviewer has a fresh context and isn’t attached to the code. /loop is built into Claude Code; with no interval it picks its own pace, checking often while the PR is active. A bare /loop with no prompt tends the current branch’s PR by default. gstack’s /review is an alternative reviewer.
